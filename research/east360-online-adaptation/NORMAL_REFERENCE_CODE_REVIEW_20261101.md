# Normal-reference coordinate interface: bounded code review

**Scope and disposition.** CPU-only, read-only review apart from this file; no GPU experiment was launched and no running code was edited. The coordinate interface is a reasonable numerical continuation of the same *ideal* source-asinh maps, not evidence that those maps are physically valid or useful. The original four candidate arms have no complete v1 result. The current run was still in progress when inspected; this review makes no claim about its final metrics. References below are relative to this worktree and use the inspected line numbers.

## Actionable implementation and verification findings

1. **The claimed numerical-equivalence check records discrepancies but does not enforce or classify them.** `experiments/risk_aligned_online/normal_reference_alignment_20261031/run_coordinates.py:142-167` saves each old/new maximum probability error and the number of threshold-point differences, but there is no tolerance, failure condition, or explicit equivalence verdict; `run_coordinates.py:244-259` can still write `COMPLETED` for arbitrarily large disagreements. The summary mixes the first 20 identical, unmapped warmup shots with genuinely mapped prefix shots, and a count of threshold-point flips is not a recount of first-alarm/timely-TP/FP changes. The existing synthetic roundtrip test compares coordinates, not the original network's outputs after the old versus new mappings (`tests/test_normalized_forward_20261101.py:72-108`); its identity-forward test supplies Torch-generated levels, rather than exercising the actual NumPy-to-Torch coordinate pipeline (`tests/test_normalized_forward_20261101.py:25-34`).

   **Action after the current run:** independently compare old and new mapped-prefix logits/probabilities by arm and shot, excluding warmup from the mapped summary; report maximum/quantiles and inspect every threshold crossing with the first-alarm and lead-time rules. Declare an explicit tolerance and separately report discrete alarm changes, rather than interpreting a written `COMPLETED` as an equivalence verdict. Add end-to-end old-raw-vs-coordinate forward checks with the real center/scale, varying masks, and near-threshold inputs. Do not turn the incomplete old prefix into a full-stream candidate score.

2. **A valid all-missing/no-active-observation shot crashes in diagnostics.** `coordinate_signal` deliberately supports an empty observed pattern (`experiments/risk_aligned_online/normal_reference_alignment_20261031/normalized_forward.py:27-33`), and the embedding hook passes missing coordinates through (`normalized_forward.py:75-89`). Nevertheless `run_coordinates.py:50-53` calls `max()` on an empty selection. I reproduced `ValueError: zero-size array to reduction operation maximum which has no identity` on CPU with a one-row, all-unavailable signal and a finite source model. This is a real edge-case defect, **not** a claim that an observed current-run shot has triggered it; the saved maps currently select 21 channels. A subsequent revision should record an observed count and use a nullable/no-observation maximum, allowing the original pass-through prediction to complete, with a regression test for no observed active coordinates.

3. **Map provenance is recorded but not fully enforced by the new runner.** The old `completed.json` is pinned and an audit status is read (`run_coordinates.py:68-71`), but those checks do not bind the four map file bytes to that audit. At rank 20 the runner checks only `first_affected_rank` and that the saved target IDs are a subset of the first 20 (`run_coordinates.py:199-215`); it does not itself verify exact pooled/safe identities, map mode/active/status, statistics, or preceding seals. The map hashes are computed after loading, not compared to a previously pinned map manifest. `ended_groups` checks seal syntax and identities, not whether those hashes actually prove the claimed temporal event (`experiments/risk_aligned_online/normal_reference_alignment_20261031/core.py:18-40`). This is an **enforcement/audit gap**, not evidence of altered maps or future-label leakage.

   Reassurance from this review: each of the four currently saved maps' source, target, mode, active/status, ridge and direction fields exactly matched `make_transport` applied to the recorded source/target statistics. This is a same-implementation consistency check, not independent statistical verification. The existing v1 independent audit also recomputes the statistics and checks map-to-statistic and old-seal correspondence (`experiments/risk_aligned_online/normal_reference_alignment_20261031/verify.py:150-191`), but a `PASS` is not itself a content-addressed binding of the maps loaded by this run. After completion, compare the new `map_access.json` hashes with preserved old map bytes, independently check exact target group membership and all fit fields against the historical receipts/statistics, and bind future runs to an immutable map manifest. Do not modify the live run to do this.

## Causal access and the original network

- In the inspected prediction path, the map is fixed from rank 21 onward; raw signals are read without outcome metadata (`run_coordinates.py:127-141`, `experiments/risk_aligned_online/io23.py:62-96`), each score window ends at the requested endpoint (`experiments/risk_aligned_online/simple_data.py:41-48`), predictions are sealed before the current outcome is attached (`run_coordinates.py:168-187`), and the saved maps are loaded only after the twentieth seal/reveal (`run_coordinates.py:199-218`). Pointwise mapping plus past windows provides functional within-shot causality conditional on the fixed map. The implementation nevertheless materializes the **whole current shot** before prediction and opens old per-shot curves before the new seal; the ledger is a sequencing check, not an access sandbox. These facts do not by themselves show that a future value or current label entered a prediction. A prefix-perturbation end-to-end check is appropriate before a stronger access-control claim.
- The order is **not historical online chronology**: the inherited cold20 was chosen using saved initial-100-ms current prefixes of future shots and an offline rank-stratification rule (`STRATIFIED_COLD20_PLAN_20261031.md:17-24`). The target map may be causal with respect to this stipulated replay while the schedule itself uses future-prefix knowledge. All 360 were exposed during development, so neither this scheduling nor outcome comparisons are an independent prospective confirmation.
- For the actual `Simple23` source view, `simple23.py:74-107` constructs each time step as 23 asinh levels followed by 23 availability flags, then flattens patches. `normalized_forward.py:75-93` reshapes that exact interface, replaces only `observed & active` level slots, calls the original model and removes the hook in `finally` (`normalized_forward.py:91-100`). Thus the embedding weights, transformer, risk/forecast heads, mask features, padding and inactive channels remain the original ones, while the **function's input representation is deliberately changed**; mapped predictions are not the original model's unmodified predictions. State equality and hook cleanup (`run_coordinates.py:225-231`) support unchanged parameters, not equality of transformed outputs or physical representability. Concurrent use of the same model object would need separate hook isolation; the inspected runner is sequential.
- `MNM` and `mode_number_n` are explicitly excluded; columns with fewer than three observed calibration shots or zero estimated variation also pass through (`core.py:162-187`). Missing CIII sentinels are masked pointwise on EAST, and no missing or padding value is inserted as an observed zero (`experiments/risk_aligned_online/causal_input.py:87-105,126-133`; `normalized_forward.py:64,75-89`). In all four saved maps 21 channels are active; CIII has sampled observations in 15/20 pooled and 10/12 safe target shots. This does not certify their physical semantics or statistical coverage.

## v1 numerical failure versus statistical interpretation

- The original `core.py:215-225` maps to source-asinh coordinates and then performs `sinh` and a float32 raw-range check, although the next source model immediately applies asinh. In v1, pooled arms failed at rank 119 / shot 73403 and safe arms at rank 154 / shot 63656 (`probe_outputs/normal_reference_alignment_v1/candidate_failures.json`). The old runner explicitly omits failed arms from full-stream scoring (`experiments/risk_aligned_online/normal_reference_alignment_20261031/run.py:144-157,255-265`); its completed file contains only source and density metrics. The old independent audit's `PASS` is about the checks and complete arms it actually audited, not proof that any failed map succeeded or failed scientifically.
- A targeted CPU calculation on these two shots independently encountered the stated representability problem: for shot 73403 the pooled diagonal and correlation maps had max |coordinate| about 93.51 and 92.80, with one float32-raw overflow each; for shot 63656 safe diagonal and correlation reached about 100.36 and 103.15, with three and four overflowed coordinates respectively. These are coordinate-interface calculations, not replayed GPU predictions. Bypassing `sinh` removes that particular avoidable storage/roundtrip failure. It does **not** make huge coordinates typical of source training, prove finite downstream outputs for all possible finite inputs, or establish physical plausibility.
- The original map is mathematically specified in coordinates, but float32 raw quantization and Torch-versus-NumPy normalization mean old and new finite-range execution need not be bitwise equal. On the representable portions of the two CPU spot checks, the maximum coordinate roundtrip discrepancies were approximately 2.4e-7 to 3.6e-7. This spot check used the new float32 coordinate as the inverse-transform input, so it is not a replacement for the saved old-curve comparison or a complete reproduction of the old float64 intermediate.

## Known statistical and design limitations, not newly discovered implementation faults

- The weighting is not simply equal shot weight for every channel in the presence of missingness. Each shot gets total sampled weight one, but its contribution to a channel falls with the fraction observed; standardized missing entries are then zero-imputed and the covariance is renormalized to correlation (`core.py:83-118`). Timepoints within each shot are correlated. Missingness-dependent selection can bias the resulting moments and pairwise correlations; restricting inference to observed principal submatrices does not turn the estimates into pattern-conditional or missingness-unbiased covariances. The original plan explicitly discloses this (`NORMAL_REFERENCE_ALIGNMENT_PLAN_20261031.md:26-32`).
- The source reference uses 1,353 pooled / 1,165 safe shots, while the target uses only 20 pooled / 12 safe ended shots. Standard deviations are checked only for being nonzero and for at least three observed shots, not for stability (`core.py:165-175`). For CIII, saved pooled source/target SDs are about 0.6343/0.02185 and safe SDs about 0.6217/0.02367, so the diagonal scale ratios are roughly 29.0 and 26.3. Tiny target variation and changing missingness can therefore amplify moderate target departures substantially; being finite after the repair does not resolve this sensitivity.
- The correlation map is correctly oriented target-to-source **for the regularized matrices**: `A=(Ct+I)^(-1/2)(Cs+I)^(1/2)` and `A.T(Ct+I)A=Cs+I` (`core.py:132-159`). It does not generally make `A.T Ct A = Cs`, nor preserve the diagonal after recoloring. On the stored full 21-active-channel estimated matrices, my CPU calculation found max unregularized entry differences of 0.437 pooled and 0.532 safe, with transformed diagonal ranges 0.690–0.991 and 0.561–0.922 respectively; regularized identity residuals were below 1.3e-14. These are algebraic diagnostics on the saved mean-imputed estimates, not empirical post-map moments or conditional-on-pattern estimates. Ridge=1 is predeclared; do not retune or clip the current run after looking at the outcome.
- Pooled and ended-safe maps answer different descriptive comparisons, and safe-only alignment does not guarantee that disruptive trajectories align. Full-shot calibration samples include any recorded post-terminal points by design (`NORMAL_REFERENCE_ALIGNMENT_PLAN_20261031.md:24-28`); they are from ended shots, so not automatically future leakage, but their proportion can alter the reference. Mapping variance-like columns to negative implied raw values and changing cross-channel/operating relationships remain physical risks. Report negative-variance counts and extreme coordinates alongside paired shot-level alarm results; do not infer intra-shot learning, a calibrated physical conversion, or causal efficacy from distribution matching alone.
