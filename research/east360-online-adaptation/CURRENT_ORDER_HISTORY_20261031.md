# Current-only order: bounded history audit

2026-10-31. Scope: read-only inspection of the named MAIN and WT histories, except for this report. No GPU, model replay, training, raw-data writes, experiment-code changes, or selection of an order using outcomes. The results below are development-exposed, not independent validation.

## Verdict

**There is prior art for the exact proposed *global ordering of these 360 identities*, but the bounded search did not find a completed current-only comparison on this 360-shot set with the planned first-20 refit procedure, source `c7270c…`, context8 source memory, and the same lifecycle neural methods.** It is therefore **not established as a duplicate experiment**. This is a search-bounded conclusion, not proof that no other archive exists. In particular, a pre-existing ordering file is not proof that the corresponding 360-shot model replay was performed.

The meaning of “same cold20” is now explicitly confirmed: **the same 20-shot startup *procedure and budget*, not the same identities or previously fitted state.** The [current-order plan](</media/hetaisheng/044A81D94A81C83E/Fuison-intra-trajectory-20261028/CURRENT_ORDER_PLAN_20261031.md>) specifies refitting the map and cold state solely from the *new* first 20, with no reuse of the old cold state. Its stated status was `NOT_YET_RUN` when inspected; this audit did not execute it. Only 8 original cold20 identities occupy the new global first 20. Reusing the old fitted state at that point would expose information from 12 original cold shots before they occur in the new order, but **that is not the planned protocol**. The refit changes fitted data and state as a consequence of the order, so an end-to-end difference cannot be attributed solely to changing the order of a frozen predictor. Keeping the original cold20 as a prefix and sorting only the remaining 340 is a different, unrequested comparison and would **not** globally sort all 360.

## Exact ordering comparison, using saved prefix values

The proposed key was calculated from the 360 archived `initial_ip_A` values as `((initial_ip_A/100000)^2, shot_id)`, before joining any outcome. All 360 saved currents are distinct, so no tie occurs in this particular roster. This calculation reuses saved medians; it is not a fresh scan of the raw 100 ms signals. **Blinding caveat:** this audit did not persist a new order manifest/hash before joining the saved outcomes, as the subsequently inspected current-order plan specifies. The ordering rule was supplied in the user request before this audit, and no outcome was used to select it, but the composition is now exposed; do not describe this audit itself as a blinded or newly pre-registered ordering exercise. Whether the main process independently locked an order beforehand was not checked.

The user confirmed that this newly disclosed composition does not change the specified order. Under the current HDF5 labels, two safe startup shots do not establish adequate coverage of normal operating conditions; reordering alone does not resolve the normal-coverage limitation. The label disagreements described below remain unresolved.

There are 2 equal positions across the full two 360-shot sequences, and the largest absolute rank displacement is 271. The original cold20 have global-current ranks from 1 through 37; 12 lie after position 20. For example, `87494` moves from old rank 124 to new rank 7, while original cold shot `70418` moves to new rank 37.

For the *different* fixed-prefix alternative, preserving the original cold20 in their original order and sorting the old suffix340 by current changes 339 of the 340 suffix positions. Its first ten suffix IDs are `87494, 79712, 79604, 90874, 78789, 83646, 83346, 89881, 87484, 87508`. There are 191 cold/suffix cross-boundary current-rank inversions, so the resulting 360 sequence must not be described as globally current-sorted. Inter-shot adaptive states must evolve in the new history; reusing a later old-order state would not preserve causality merely because the initial cold checkpoint is identical.

For the planned global sort with a **new** cold fit, the old source-only predictions are reusable in principle if the exact input contract and source are preserved, because the archived runner computes that arm from the original source per shot. The mapped/cold/intra curves cannot simply be imported from the old run: their fitted map or cold model changes with the startup identities. For the distinct fixed-old-prefix alternative, inspection of the archived runner and context trace indicates that source, aligned, cold and intra use the same frozen per-shot inputs/state after that prefix; their sealed per-shot curves should be reusable subject to receipt/input/code verification. Their full-set counts would then be the same, though sequence/block summaries change. Inter/both evolve persistent state and history, so their old-order curves cannot be assumed reusable. This is code-based reuse reasoning, not a new replay.

## Label and search boundaries

The [locked manifest](</media/hetaisheng/044A81D94A81C83E/Fuison/config/splits/east_hdf5_authoritative_balanced360_v1.json>) is HDF5-authoritative; it is a selected, development-exposed balanced cohort, not the entire 2,953 or a certified independent future sample. The existing [time/label audit](</media/hetaisheng/044A81D94A81C83E/Fuison-intra-trajectory-20261028/TIME_LABEL_AUDIT_20261031.md>) records **18** disagreements with the original TEST class lists. Examples affecting the global current first20: `74087` and `90874` are HDF5 disruptive but TEST-list safe; `83646` is HDF5 safe but TEST-list disruptive. Ground-truth adjudication remains open. Composition counts above were joined *after* ordering and are not ordering inputs.

I compared direct child `order.json` files in MAIN `experiments/risk_aligned_online/runs` and WT `probe_outputs`: **80** files examined; **33** have exactly the current 360 set and old order, **1** has the same set in another order (shot-ID order), and **46** have a different roster. None equals the global current-only or fixed-cold20/current-suffix sequence. I also parsed direct-child `protocol.json` (396), `per_shot.json` (142), and `roster.json` (33) for their top-level order/shot-list fields, and inspected the named history reports and parent/pilot artifacts. Protocol `shot_ids` can be a roster rather than execution order, and an advertised 360 order does not itself establish completed execution. Nested or differently named files, other worktrees, remote stores, deleted material, and unexamined compressed snapshots are outside this bounded search.

The historical lifecycle snapshot, rather than a later live runner, is the relevant execution reference: the existing [input-pipeline audit](</media/hetaisheng/044A81D94A81C83E/Fuison-intra-trajectory-20261028/INPUT_PIPELINE_AUDIT_20261031.md>) reports a source-memory-loading code difference between the archived runner and an earlier live WT version. The archived code loads memory into the cold model and copies its state to inter/both; a difference in resulting behavior has not been established here. Matching source SHA alone does not establish matched code, memory, cold state, labels, or causal execution.

**User-supplied clarification, not independently verified in this addendum:** the live context-model difference adds an `expected_forecast` hook that returns `None` and a scaled subclass unused on this path; the core old model, learning, and alignment are reported byte-equal. A CPU exact comparison of the archived context8 path is planned separately. This audit did not perform that comparison or any further experiment, and does not claim behavioral equivalence from the reported code differences alone.
